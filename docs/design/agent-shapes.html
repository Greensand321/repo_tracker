Shapes it could take
five layers · not five alternatives
17 Sep 2026 · nothing here is built a thing to argue with

First: how does it know when it is done?

Today the question does not exist. One request, one reply — done is the response arrived. And yes: if you want a summary, it reads twenty-five commit messages and writes a paragraph. It cannot look anything up, so there is nothing to finish.

The moment a worker can use tools, "done" becomes real, and there are three possible answers. The right design uses all three, layered — each one catches what the previous one misses.

The thing that makes a room of agents workable here: almost every job Bearing has has a predicate. "Summarise this branch" is done when a summary exists at this head SHA. "File this branch" is done when it has a goal. That is unusual — most agent systems have to take the model's word for it. Here we almost never do.

The exception is judgement — is this goal done? — which has no predicate and is why it stays a proposal you accept (D64).
The number that tells you whether any of this is working: how often a worker claims done and the predicate disagrees. Log it from the first day. If it climbs, the tools are wrong or the job is too big — and you will not notice any other way.

Five shapes

They stack. Each one adds a capability to the one above and keeps everything it had. You can stop at any level, and the level you stop at is a real decision rather than a compromise.

①

The assembly line

what is built today

Fixed stations in a fixed order. Each is one prompt with everything it needs already written into it. Nothing decides anything about what to do next.

Impossible to surprise you — and cheap
Sees only what we thought to send it
Every failure is one prompt, one fix
Cannot check a hunch, so it hedges instead
②

Stations with tools

smallest real upgrade

The same line, but a station can ask for what it needs. This is where "these models are capable of so much more" actually cashes out — not in orchestration, in evidence.

The biggest quality jump for the least structure
Needs tool calling to work on your provider
Reads the dated history that nothing has read yet
Slower and dearer per branch; needs a cap
③

The job board — the room

★ the one I would build

Work is derived onto a board every read. Workers claim jobs and run in parallel. Each is a fresh instance with tools, and every job carries the predicate that decides whether it worked. No one is in charge, because the board is the coordination.

Every job carries its own proof of completion
Parallelism buys latency, not capability, at your size
Adding a job type is adding a row, not a pipeline stage
A dispatcher, a claim, and a retry rule to get right
Failures park as questions instead of vanishing
Concurrent writes to Plane B need a lock
Most of this already exists. assist() already derives "branches needing a summary / a vision / an assessment" on every pass — that is a job board. It is just consumed by a for loop instead of by workers. Swapping the loop for a dispatcher and giving each worker tools is a smaller change than the diagram suggests.
④

The foreman

I would skip this

An agent reads the board and decides what matters and in what order, then dispatches. Adds judgement about priority that the board does not have on its own.

Genuinely useful once the board is long and mixed
An LLM deciding what plain code could decide
Could weigh cost against value per job
Its reasoning is invisible, so skipped work is a mystery
⑤

The desk — the advisor that can act

★ on top of ③

Your idea, and it is a good one. You talk to the advisor. It answers straight away from what it can already see — and when something needs doing, it puts a job on the board rather than doing it while you wait. One way out, never blocking.

Keeps the two-second answer — work never blocks the reply
"I've started that" is not the same as "it's done"
Every question stays cheap; only dispatched work costs
Needs a way to see what you set going, and cancel it
Fresh advisor each turn — it cannot drift over a long chat
The transcript is memory, and memory rots if unbounded
On the relay you described — one agent works, a fresh one reads the chat and carries on. That is exactly right, with one correction: the chat should not be the handoff. The board and Plane B are. The transcript is only how you follow along. Otherwise the conversation becomes the database, and a conversation is the worst database there is.

What tools would actually buy

Concrete, because "more tools" is easy to say. Each of these changes an answer that is currently a guess into one that is checked.

ToolCostsWhat it fixes
repo_readme(repo)one GitHub call, everGrounds every vision in what the software is. Read once per repo and cached forever — the single cheapest quality win here.
commit_files(sha)one GitHub call“Drifted” stops being a guess from commit subjects. Which files changed says more about intent than any message.
what_changed(since)free — reads diskThe dated history has been accumulating since Stage 1 and nothing has ever read it. This is what it was written for.
sibling_branches(goal)free — in memoryLets a worker see the branches next to it, which is what filing and overtaken-detection really need.
pr_reviews(repo, n)one GitHub call“Blocked” currently means red CI. A reviewer asking for changes is just as blocking and is invisible today.
dispatch(job)freeThe one write tool the advisor needs for ⑤. It queues; it does not do.

What I would do

Build ③ with ② inside it, then put ⑤ on top. Skip ④.

  • ③ before ②, narrowly — because the dispatcher and the predicate check are what make a tool-using worker safe to let loose. Tools without a predicate is just a longer guess.
  • Skip the foreman. The board's ordering is a sort, and a sort is code. Paying a model to decide what an ORDER BY decides buys you an invisible reason for every job it quietly skipped. Revisit if the board is ever genuinely long and mixed.
  • ⑤ last, because it is the one that changes how the thing feels, and it wants ③ underneath it to dispatch into.
The gate, and why it is smaller than it looks. Everything from ② onward needs the model to call tools, and that has never been tested on your plan. But npm run probe tests two mechanisms: native tool calling, and a plain JSON protocol that needs no tool support at all and works on any model that can return JSON — which yours demonstrably can, since all six prompts already do. So the probe decides which mechanism, not whether. There is a floor, and the floor works everywhere.

Open questions

  • Q68 — How many workers at once? Two is what the summariser uses today. More is faster and makes a runaway cost arrive faster too.
  • Q69 — Should you see the board? It is the honest view of what the assistant is doing and about to do. It is also one more thing to look at. Leaning: a count in the dateline, the full board behind a click.
  • Q70 — What happens to a job you cancel mid-flight? There is a real difference between "stop" and "undo", and Plane B is reversible, so both are possible. Worth deciding before it matters rather than after.
  • Q71 — Does the advisor tell you when dispatched work finishes? A notification is a product decision, not a technical one. The alternative is that it simply appears, which is quieter and matches everything else here.
