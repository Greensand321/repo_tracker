1. Overview

Bearing is a local-first tool that reconstructs your working context from signals you already produce (git reflog, working tree, stashes, commits) plus GitHub metadata (PRs, reviews, CI). It produces a prioritized brief — a short, human-readable answer to "where was I?" — and optionally enriches it with an LLM summary of work-in-progress and a suggested next step.

It is designed around one insight: the expensive part of switching tasks is not the work, it is rebuilding the mental model. Every feature is judged by how much time-to-first-productive-action it removes.

Phase 0

Read local git + GitHub, emit a Markdown brief. No LLM required.

Phase 1

Reflog session reconstruction, parking notes, LLM WIP summaries.

Phase 2+

Dashboard, hygiene radar, analytics, conversational agent.

2. Problem & Motivation

Observed by the user:

  • Dozens of open branches across ~4 projects.
  • Resuming work is slow: even a lunch break can cost up to an hour of ramp-up.
  • The bottleneck is tracking which branch holds which piece of work and what state each is in.
  • Existing tools (GitHub UI, git status) show facts, not a narrative of intent.

Root causes:

  1. Working memory spillover. Branch state lives in the developer's head, not on disk.
  2. Unbounded branch count. Stale/abandoned branches create background noise and merge risk.
  3. No session boundary. Git records commits, not "what I was in the middle of."
  4. Scattered signals. Local state, GitHub PR/CI state, and intent live in different places.

3. Goals & Non-Goals

Goals

  • Restore context after an interruption in < 1 minute.
  • Give an at-a-glance state of every branch across every configured repo.
  • Surface the next concrete action per active branch.
  • Reduce branch count by flagging stale, abandoned, merge-ready, and conflict-prone branches.
  • Be local-first and fast. v1 is fully deterministic — no LLM, no network required.

Non-Goals

  • Not a CI/CD tool or a replacement for the GitHub UI.
  • Not a team/management analytics product (v1 is single-developer).
  • Not an autonomous agent that merges, pushes, or rewrites history.
  • Not a note-taking app — parking notes are one-liners, not a journal.
  • No generated content — no LLM-invented branch names, summaries, or prose in v1. Identity and naming come from git.
  • No mandatory cloud service or account beyond a GitHub token.

4. Core Concepts

4.1 Branch State

A normalized snapshot of one branch: position, divergence, activity, working-tree changes, PR/CI, and derived flags.

4.2 Session Reconstruction key idea

The git reflog records every HEAD movement with a timestamp (checkouts, commits, rebases, resets, merges, stash operations). Bearing groups reflog entries into work sessions by detecting inactivity gaps (e.g. > 30 min), producing a timeline of "what I actually did, in order, across which branches."

This is the mechanism that answers "where was I?" without asking the user to maintain any state. It is the single most important differentiator. Most tools ignore the reflog.

4.3 The Brief

The primary output. A prioritized, scannable document with sections:

  1. Pick up where you left off — the most recent branch, enriched with WIP + next step.
  2. Other active work — recently touched branches still in flight.
  3. Needs a decision — stale, diverged, merge-ready, or conflict-prone branches.
  4. Parking notes — anything you explicitly left for yourself.

4.4 Parking Notes

Before stepping away you can run bearing park "one line". It is stored against the current repo/branch and resurfaced in the next brief. A lightweight, deterministic substitute for fragile self-memory. Scope: a scratchpad. One line, enough to resume a line of thinking later — not a journal, not structured data.

4.5 Naming

Branches are always displayed by their literal git name. Bearing never generates or substitutes display names — recognition comes from your own naming discipline, and identity stays unambiguous when you go back to the terminal. The only personal layer on top of git identity is the parking note.

6. Feature Set & Phases

Phase 0 — Brief (local, deterministic)

  • Discover configured repos and enumerate branches.
  • Compute branch state: ahead/behind, working-tree counts, stashes, last activity, diffstat.
  • Parse reflog into recent actions and a last-touched ordering.
  • Emit a Markdown brief ordered by recency, with attention flags.
  • No LLM, no network required.

Phase 1 — Context

  • Reflog session reconstruction with timeline (bearing sessions).
  • bearing park scratchpad notes, resurfaced per branch.
  • GitHub PR/CI enrichment (merge-readiness, reviews) via gh CLI passthrough — no token management.

Phase 2 — Surfaces & Hygiene

  • Shell-startup one-liner (bearing shell-init) — the brief meets you on every terminal open.
  • Fleet dashboard (bearing open) — a renderer over the same Brief JSON, in three switchable views (§14.2): The Bridge (resume-first, default), The Map (spatial), The Logbook (timeline). Literal git names throughout; advisor panel deferred to Phase 4.
  • Hygiene & Risk Radar: stale, old-base, merge-ready, conflict-prone, safe-to-delete.

Phase 3 — Insight optional

  • Velocity & churn analytics; hotspot files (frequent change × size); file coupling (files that change together).
  • "Almost done" detection and "decision debt" (branches representing unmade decisions).

Phase 4 — Advisor & LLM built last, on purpose

  • LLM WIP summaries and suggested next steps — only once every underlying data layer is complete and stable.
  • Conversational advisor over the full data layer — it draws from all Bearing data, so it is never started half-finished.
  • Caching keyed by branch head SHA; budget caps (see §9).

Layers are independently replaceable. Renderers and the LLM summarizer are optional: the Analyzer output (the Brief JSON) is itself the product, and any surface can render it. This is what allows the same engine to back a CLI, a web dashboard, a VS Code panel, or a conversational agent.

9. LLM Usage & Cost DEFERRED — PHASE 4

Nothing in this section is built until Phase 4, when the advisor starts. v1 ships with none of it. Kept here so the eventual design is already thought through.

  • Deferred. v1 delivers a deterministic brief from git facts — the LLM is a Phase 4 addition, not a dependency.
  • Granularity: one request per active branch (not per commit).
  • Payload: compact — branch name, base, commit subject lines, diffstat, notable hunks, TODO/FIXME, PR title. Not full diffs unless small.
  • Model: a cheap/fast model is sufficient (summarization, not reasoning).
  • Caching: key = {branch, headSha, configHash}. Repeat runs on unchanged branches are free and offline.
  • Budget controls: max requests per run, max tokens per request, hard skip above a diff-size threshold.
  • Endpoint: OpenCode Zen (pay-as-you-go, OpenAI-compatible). See §10.
Billing note: this is a personal automation, not a coding-agent workload. Use Opencode Zen (per-token) rather than the Go subscription, whose terms target coding agents and monitor for abuse.

10. Privacy & Security

  • Local-first. Repo contents never leave the machine unless the LLM summarizer is enabled.
  • When enabled, only the minimal excerpt needed for a summary is transmitted; full history is never uploaded.
  • GitHub token read from environment or OS keychain; never written to config in plaintext.
  • No telemetry. No account creation by default.
  • Read-only against repos: Bearing never pushes, merges, rebases, or deletes without an explicit, separate command.

12. CLI Surface (proposed)

CommandPhaseDescription

bearing sessions [--days 7]1Reconstructed work sessions / timeline.
bearing add .1Register the current directory as a tracked repo (appends to config).

Cut from v0.1: bearing scan (redundant — the brief is always computed fresh), bearing config (edit the TOML directly), and scheduled digests (shell-init covers the morning case). Fewer commands, fewer tests, less to learn.

13. Delivery & Stack DECIDED: PYTHON ENGINE

Decision (v0.3): a Python engine over a pure core, calling the git binary via subprocess (no heavy git bindings) and gh for GitHub. The owner's daily surface is the dashboard, not the terminal — so the local web view is a committed Phase 2 deliverable (§14.2), served by the same Python process. No JS framework required for v1; the three-view designs are specced in §14 and prototyped in this repo. Ordering still matters: Phase 0 builds and tests the engine; the dashboard is a renderer over tested Brief JSON, which is what keeps the leap from backend to frontend cheap. Electron and VS Code stay out.

OptionProsCons
A. Python CLIFastest to build; excellent git/GitHub libs; best engine for later UIs.Distribution needs packaging; UI requires a second layer.
B. Node/TypeScript CLIShares language with a future web dashboard / VS Code extension.Slightly heavier tooling; git plumbing less ergonomic than Python.
C. Python engine + local web UIBest of both: reusable engine, rich dashboard.Two components to run; more moving parts.
D. Electron desktop appAlways-available, native-feeling tray app.Heaviest; slowest to first value; overkill for Phase 0.
E. VS Code extensionLives where you code; status bar + panel.Editor-locked; can't be used from a plain terminal.
F. Go single binaryTrivial distribution; fast startup for shell hook.Slowest iteration; fewer high-level GitHub conveniences.

Recommendation: A now, then C — start with a Python CLI over a pure engine, add a local web dashboard in Phase 2. Electron/VS Code are postponed until the engine proves itself.

14.2 — Dashboard: three views (Phase 2) THE VISION

The owner's daily surface is the dashboard, not the terminal. One dashboard, three switchable views — all renderers over the same Brief JSON. Interactive prototypes: The Bridge · The Map · The Logbook. A static Bridge snapshot is delivered early (Phase 0, bearing brief --html) so the tool is visually usable from day one; the interactive three-view dashboard follows at Phase 2.

The Bridge (default)

Dashboard-first, resume-first. One clear thing on top: a "pick up where you left off" card — last-touched branch, last actions, uncommitted files, next step. Below: attention flags (merge-ready, uncommitted, stale decisions), then per-project lanes of branch cards.

The Map

Spatial overview. Projects as islands, branches as trails whose warmth encodes recency — walked today glows, weeks-old grows moss, stale goes dashed. "You are here" marker on the active branch. Hover for state; click for the dossier.

The Logbook

Timeline-first. The week as one interleaved stream across branches — commits, notes, parks, CI events — answering "how the work unfolded," not just where it stands. Feeds off session reconstruction (Milestone 1).

Translation rules, prototype → product:

  • Literal git names everywhere. The prototypes' invented display names ("The token refresh thing") are exploration artifacts — the product shows repo / branch-name. Recognition comes from naming discipline (§4.5).
  • Notes are scratchpad one-liners (§4.4) — rendered on cards and in the dossier, never prose blocks.
  • No advisor panel until Phase 4. The prototypes' advisor rail becomes a deterministic "next actions" list derived from flags.
  • Shared across all three views: the dossier drawer (branch detail — note, ahead/behind, activity, session story) and the attention flags bar.

16. Rollout Plan

  1. Milestone 0 — repo discovery, branch state, Markdown brief (no LLM, no network).
  2. Milestone 1 — reflog sessions + parking notes + bearing add.
  3. Milestone 2 — gh PR/CI enrichment + merge-readiness flags.

  5. Milestone 4 — analytics (optional; only if still wanted).
  6. Milestone 5 — LLM summaries + conversational advisor, built last on the complete data layer.

17. Open Questions

Resolved in v0.2

  • Delivery surface — Python CLI (§13). The dashboard is deferred until the brief proves itself in daily use.
  • LLM in v1 — No. Fully deterministic first; LLM arrives with the advisor in Phase 4.
  • Advisor timing — last, by design. It draws from all Bearing data, so building it early means building it half-finished.
  • Branch display names — literal git names only (§4.5). No generated names.
  • Brief cadence — on-demand plus shell-startup one-liner. Scheduled digests cut.
  • GitHub auth — gh CLI passthrough. If gh isn't authenticated, GitHub features silently no-op.
  • Safe-to-delete — list-only, permanently (read-only principle).
  • Exclusions — default skip-list: dependabot/*, renovate/*; configurable.

Still open

  • Windows-first details: PowerShell profile hook for shell-init, path handling in config.
  • Reflog timestamps need normalization when comparing activity across repos — trivial, but note it.

18. Appendix: Heuristics & Defaults

FlagHeuristic (default)
activeTouched — via reflog: checkout, commit, rebase, not just commits — within staleness_days (7).
staleNo activity for ≥ staleness_days and not merged.
divergedBehind base by > 20 commits. (v0.1's "> 3× ahead" rule removed — a branch that's far ahead is finished work waiting to merge, not a risk.)
conflict-riskFiles changed on both branch and base since fork point.
merge-readyOpen PR + passing CI + required approvals + no conflicts.
safe-to-deleteMerged into base, or no unique commits vs base. ("Superseded" removed — uncomputable without guessing intent.)
almost-donePR open, CI green, approvals present, untouched > 1 day (nudge to merge).

All thresholds configurable.
